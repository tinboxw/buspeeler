# EST 串口参考标注与固件分析评估

日期：2026-09-22。状态：已完成手册核对、固件集合初筛和一个样本的局部静态分析；尚无实车串口/CAN 同步记录、完整反编译或已验证 DBC。

协议基线已按用户更正为 `EST580车联网CANBUS模块数据手册_内部版本.pdf`；先前提供的 EST558S 手册保留原文件，但不作为本项目 EST580 字段解释依据。

## 1. 结论与适用范围

两条路径都值得纳入 buspeeler：

1. 将现有 EST 工具作为**串口参考源**，与周立功/创芯采集的原始 CAN 同步记录，自动生成参考曲线和状态变化标签，减少逐次人工标注。
2. 对已提供的车型固件做离线静态分析，提取工具实际使用的 CAN ID、位段、换算和条件，作为带证据的**固件派生候选**，缩小自动搜索范围。

本次已经找到连贯的 CAN 接收、ID 分支、字节换算和串口格式化调用，不只是文件名或字符串猜测。因此可以继续恢复样本中的具体规则；但不能据此承诺完整恢复全部 94 个固件，更不能恢复固件从未使用的整车原厂 DBC。

同一个 EST 固件同时充当规则来源和参考输出时，两者一致只能证明复现该工具的行为。它们存在共同错误来源，不构成物理语义的独立验证，不能自动推进到 validated/published。

## 3. 手册能确认什么

下表以更正后的 EST580 内部版手册为准。手册 39 字段是解析基线，具体固件仍需检查字段支持情况、扩展和实际输出。

| 来源 | 手册规定 | 用于标注的边界 |
| --- | --- | --- |
| 第 2 页串口参数 | UART；波特率列出 9600/38400/115200 | 没有在该表指明默认值；实际波特率、数据位、校验位、停止位、流控和电平另验，不把 8N1 假定写成手册事实 |
| 第 5、7 页 `$OBD-RT` | RT 默认打开，默认 5 Hz；ATEHZ 标称可设 1–20 Hz | 周期快照，不是每条 CAN 帧的实时真值；不沿用旧手册的 BDT 事件上报假设 |
| 第 6–7 页 Table 5 | 39 个数据字段，含连续量、门窗、踏板、雨刷、灯光等 | 可以直接建立按位置映射的参考基线，字段存在不代表每车型都支持 |
| 第 5 页 IO 开关 | ATION/ATIOFF 控制 IO 广播，默认打开 | 此手册未给出 IO 数据布局和事件时序；不能照搬 EST558S 的 18 路定义，需固件/日志确认 |
| 第 5 页模块信息 | ATVER 获取车型代码、模块编号、软件版本和日期；ATVIN 获取 VIN | 默认接入只读取自然输出，首版不自动发送这些命令 |
| 第 7 页不支持字段 | 使用 `#` | 保存 unsupported/unknown，禁止转换成 0、false 或空挡 |
| 第 6 页转向字段 7 | 原文为“左转 R0 到 R1000；右转 L0 到 L1000” | 不擅自按字母直觉交换左右；手册未标注单位；用户已确认为百分比，R25 表示 25%，不除以 10；保留字母与数值，方向另做实测 |

默认 5 Hz 只说明该协议的广播节拍，不能据此声称参考时间精度为 200 ms，也不能把两个快照之间的值线性插值成真实轨迹。短暂灯光或开关变化可能无法被周期快照完整记录；提高频率也不能消除设备内部缓存或滤波。

39 字段映射摘要（序号不含 `$OBD-RT` 标识）：

| 序号 | 字段 |
| --- | --- |
| 1–7 | 钥匙、电瓶电压、发动机转速、行驶车速、冷却液温度、挡位、方向盘转向编码 |
| 8–14 | 加速踏板、总里程、剩余油量、平均油耗、本次行驶里程、故障码数量、本次运行时间 |
| 15–19 | 主驾驶门、副驾驶门、左后门、右后门、后尾箱 |
| 20–25 | 主驾驶窗、副驾驶窗、左后窗、右后窗、天窗、中央门锁 |
| 26–32 | 主驾驶安全带、副驾驶安全带、离合、喇叭、雨刷、手刹、刹车 |
| 33–39 | 左转灯、右转灯、位置灯、近光灯、远光灯、前雾灯、后雾灯 |

手册中的剩余油量是百分比，不能沿用旧手册的升；当前 RT 字段中没有单独的“双闪灯”列，不能把两转向灯同时为 1 直接命名成已验证双闪状态。VA3 样本的 RT 第 3/4/7 字段分别与转速、车速、转向字符串读写位置吻合，这为语义关联提供了更强证据；12 个固件中的附加 40 字段格式仍需独立确定，不能忽略多出字段或自动平移映射。

## 4. 自动参考标注的实现设计

```text
同一车辆、已确认的总线/接入点
  ├─ 周立功 / 创芯 → 原始 CAN + 时间戳 ───────────┐
  └─ EST 工具 → 串口原文 + 主机接收时间 ────────┤
                                                 ▼
            版本匹配的解析 → 时间对齐 → 参考值/状态变化标签
                                                 │
                          CAN 候选排序与拟合 ←────┘
                                                 ▼
                       独立物理参考或人工对照验证 → 发布
```

### 4.1 串口接入

应用服务增加 Python/pySerial 参考采集模块，随 Windows/Linux 发布包提供，由本地后端枚举串口并读取，浏览器只操作页面。不依赖 Web Serial 的浏览器兼容性，也不增加独立部署服务。

默认只读串口，不自动发送 ATVER、ATVIN、ATRON、ATEHZ、复位、反向控制或升级命令。串口打开前设置流控与 DTR/RTS 策略并实机检查打开行为，不能把“不调用 write”当作绝对没有设备影响；相关行为参见 [pySerial API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html)。模块 UART 与成品设备的 USB/RS232 转接可能不同，电平和线束必须先确认，不根据供电电压推断 UART 逻辑电平。

每次接收保留原始字节块、序号、主机单调时钟时间、端口配置、设备/固件身份及异常。行解析处理半包、粘包、CR/LF、长度上限、字段数量、非法字符、未知前缀、启动消息和断线。原始记录先保存，无法解释的行进入待识别区，不能静默丢弃或自动替换为已知协议。

协议 profile 首先实现当前手册的 39 字段 RT，再为已确认的固件扩展建立独立版本；旧 EST558S EDT/BDT 不属于当前设备接入基线。头标识、字段数与固件信息用于匹配建议，不能单凭“39 列”确认所有语义和单位。未确认的扩展列保存为 field_40 等未知项；实际输出可能受配置、启动状态或分支影响，需要原始串口样本确认。

### 4.2 数据身份、时序与质量

参考记录扩展：`reference_source=est_serial`、设备型号、固件文件哈希（可获得时）、设备报告的版本、protocol_profile、字段名/原始位置、原文记录引用、raw_value、value/unit、quality、host_rx_time、时钟域、估计延迟/不确定度和证据来源组。

文件哈希只有在知道设备实际加载的是该文件时才建立对应关系；不能从车型名称推断设备当前固件。固件来源与串口来源通过共同的 `evidence_origin_group` 关联，防止验证流程把同源结果误算作独立证据。

CAN 与串口由同一主机采集时，共用主机时间基准；硬件 CAN 时间戳另做映射。串口到达时间不是车辆状态生效时间，需估计设备更新、排队、USB 和主机调度造成的延迟及抖动。每个字段可能异步刷新，不能假定一行 RT 是同一瞬间的原子快照。

状态标签保留首次观测时间和变化区间，比较连续有效 RT 快照生成变化标签。周期快照的两次观测之间存在不确定区间；长期数值不变不能证明底层 CAN 仍在刷新。结合串口在线性、设备字段刷新/超时约定判断可用性，不能无条件无限延长有效性或简单按 200 ms 判失效。断线、重启、固件切换及解析失配切断连续区间；尚未确认的 IO 上报规则单独处理。

数值字段保留量化/取整特征。用整数车速拟合高分辨率 CAN 字段时应考虑参考量化区间，不能只用逐点精确相等判断错误。转向字段保存 R/L 原文、方向字母及用户确认的百分比数值；R25 表示 25%。超过 100 保留并提示，左右映射仍需实测。需要实际角度时另接角度参考，百分比不能直接改名为角度。

### 4.3 页面流程

在“数据”页增加“参考设备 → EST 串口”：选择端口、确认参数、查看原始流和协议匹配结果；展示支持/不支持/未知字段、接收节拍、时序警告与设备身份。

在“分析”页自动叠加参考曲线和状态变化带，允许人工修正标签、排除无效片段，并保留修订来源。用户仍负责安排能排除混淆的操作；自动参考减少逐次打标签，不取消实验设计。

在“验证”页单独展示“与 EST 输出一致”和“独立物理验证通过”。只满足前者的固件派生候选不能进入正式发布；安全相关信号继续执行架构文档的更严格使用条件。

## 5. 固件静态分析的实际证据

### 5.1 分析方式与基址

本次使用现有 LLVM 工具对 VA3 `.bin` 的派生副本进行 ARM Thumb 反汇编；未刷写、执行或修改固件，也未加载已有 IDA 数据库。线性反汇编会把常量误解为指令，因此结论只使用已串联的调用和读写关系，不以整份反汇编列表作为完整代码识别结果。

样本开头为初始栈值 `0x20005698`、复位向量 `0x08006945`。采用加载基址 `0x08002000` 时，复位入口对应文件偏移 `0x4944`，可见一致的入口代码；同一基址下串口格式地址和多个代码交叉引用也一致。该样本基址有交叉证据支持，不由文件名推断；其他固件仍需分别确认。向量结构可对照 [ST Cortex-M3 编程手册 PM0056](https://www.st.com/resource/en/programming_manual/pm0056-stm32f10xxx20xxx21xxxl1xxxx-cortex-m3-programming-manual-stmicroelectronics.pdf)。

重要位置（均针对上述 SHA-256 样本）：

| 位置 | 静态观察 |
| --- | --- |
| `0x08004E7E` | 接收辅助函数读取 CAN 接收寄存器；将标准/扩展 ID 放到内部消息 `+4`，数据字节放到 `+8…+15`，长度位于 `+0x10` |
| `0x08002F08 → 0x080032D8 → 0x08002ECC → 0x080034D2` | 接收、传递消息结构到车型解码分支的路径 |
| `0x080034D2` | 根据消息 `+4` 分支，包含 `0x050`、`0x0C2`、`0x280`、`0x320`、`0x390` 等 ID |
| `0x080037F0` | 解码结果公共结构的地址常量为 `0x200000CC` |
| `0x08003F8A…0x08003FBE` | 从该结果结构读取数值，按 RT 格式调用格式化输出 |
| 文件偏移 `0xBB0C` / 地址 `0x0800DB0C` | `$OBD-RT` 的 39 字段格式字符串；指向它的常量位于文件偏移 `0x201C` |

### 5.2 已追踪的四个候选示例

下表的 byte 下标从 0 开始。**换算逻辑来自静态代码；语义、有效范围、车辆实际版本和适用条件尚未实测确认。** 不据此发布可用于控制的 DBC。

| CAN ID | 代码换算 | 结果去向与证据 | 当前解释 |
| --- | --- | --- | --- |
| `0x280` | `u = byte[2] + 256*byte[3]`；整数结果 `u >> 2` | `0x080035CC…0x080035D8` 写结果结构 `+8`；RT 输出第 3 个字段读取该位置 | 对应手册发动机转速 rpm；仍是待实车验证的静态候选 |
| `0x320` | `u = byte[5] + 256*byte[6]`；整数结果 `floor((u >> 1)/100)` | `0x080035E2…0x080035F4` 写结果结构 `+0xC`；RT 第 4 个字段读取该位置 | 对应手册行驶车速 km/h；不能把量化后的显示规则直接当成完整物理编码 |
| `0x0C2` | `u = byte[0] + 256*byte[1]`；`p = floor((u & 0x3FFF)*100/0x2E00)`；`u > 0x8000` 输出 `R%d`，否则 `L%d` | `0x0800354A…0x080035A2` 写结果结构 `+0x15` 字符串；RT 第 7 个字段使用该字符串 | 转向百分比候选；单位来自用户确认，固件保留整数换算与严格方向条件；左右映射、适用范围及与手册 0–1000 的关系仍需实测 |
| `0x390` | `byte[2] & 0x01` 非零输出字符 `1`，否则 `0` | `0x08003626…0x08003636` 写结果结构 `+0x49`；RT 第 15 个字段读取该位置 | 对应手册主驾驶车门，打开 1 / 关闭 0；仍需操作对照与独立验证 |

不能只从 `u >> 2` 推断完整原厂定义是 16 位 factor=0.25：固件可能只关心整数显示，低位、无效码、饱和、跨帧状态和物理量程仍需查明。同样，第三条规则中方向判定是严格 `>`，不能擅自改成 `>=` 或通常的符号位解释；边界可能是特例或固件缺陷。

以上仅是一个样本的局部路径。尚未完成消息过滤/长度前置条件、串口所有字段、所有写入路径、超时清零、总线物理映射和发送路径审查。样本中的 CAN 寄存器和 8 字节结构也不构成 EST 支持 CAN FD 的证据。

## 6. 固件分析如何进入产品流程

建议先对一个目标车型完成深度样本，再按程序结构而非文件名批量扩展：

1. 固定原文件哈希，识别镜像基址、代码/数据边界、公共库和差异区域；相同内容去重，但保留来源。
2. 从串口格式反向追踪结果结构，再向前关联 CAN 接收与 ID 分支；复核位操作、取整、符号、有效码、超时及初始化值。
3. 同时排查是否依赖主动诊断、轮询、会话建立或外部 IO，区分原始总线字段、设备合成状态和内部统计。
4. 导出结构化候选及证据：固件哈希、函数/指令地址、CAN ID/帧类型、数据提取表达式、后处理、串口字段、条件、未决项和来源组。
5. 用实际原始 CAN + 实际串口同步日志验证工具行为，反例回到候选修订；再用独立参考验证真实含义。
6. 仅将能被 DBC 正确表达且通过既有门槛的信号进入发布包。特殊缩放、方向拼接、累计计数、诊断会话及滤波不能静默压成 factor/offset。

固件分析是离线研发工具链，不进入普通用户发行包；用户安装 buspeeler 不需要 IDA、Ghidra 或 LLVM。已经批准的解析 profile 和候选资产以数据形式随应用导入，保留版本与来源，不执行固件或附带脚本。

从固件能够恢复的是工具实际读取和处理的规则，不保证包含所有车辆信号、原厂名称或完整 DBC。多车型字符串也可能只是公共枚举，不能因为字符串存在就宣称每个分支已经实现。加密、压缩、动态表或缺失模块若在后续样本出现，必须逐项报告；当前未分析全部路径，不能排除它们。

## 7. 被动采集与独立验证的关键限制

当前 EST580 手册第 1 页明确提及 ECU 诊断通信和动作执行（反向控制），第 9–10 页还有 IAP 升级流程。因此“buspeeler 只读串口”不能证明 EST 工具在车辆侧不发请求；周立功/创芯开启 listen-only 也只能保证自身的被动性。默认接入不得通过探测性串口写入触发配置、升级或动作执行。

目录中的“大众纯监听版本”只是文件名，不能替代硬件总线测量或固件发送路径审查。若 EST 需要主动请求才能产生某些状态，必须把该会话标成带外部主动参考设备的实验；不能纳入严格被动场景的承诺，也不能让 buspeeler 自动代发。

参考信号可能因车型不匹配、整数化、缓存保持或工具自身错误而偏差。标定时可以使用它作为教师输出，正式语义验证仍应结合人工实际状态、独立接点/传感器或可核查的独立协议依据。安全控制不能仅依据与 EST 一致或成功生成 DBC。

本次保留全部原始 PDF、BIN、I64 和 XLSX，未刷写设备、未连接串口、未发送 CAN/AT 命令、未生成实车验证结论。

## 8. 调整后的开发优先级

P0 增加协议版本确认：以当前 EST580 手册的 39 字段 RT 为基线，获取实际设备型号/固件版本及串口原文，确认 39/40 字段、转向编码与 IO 扩展；检查串口接线、电平和设备的车辆侧主动行为。

P1 在既定可视化闭环中加入串口参考接入与同步录制、质量展示、自动变化标签和同源证据提示。先实现已确认协议 profile；不为覆盖所有固件而延后基础采集/导入工作。

固件路线先完整分析一个目标车型（本次 VA3 MT 可作为已有起点），把静态候选与同步日志对照，再扩展同族固件。94 个文件是可分析资产清单，不是 94 个已适配且已验证的车型。

### 实施时补充的目标信号路径

仍针对同一 VA3 MT 2019 样本，byte 下标从 0 开始。

| 目标 | 原始字段与处理 | 证据 |
| --- | --- | --- |
| 手刹 | ID 0x320，byte[1] bit1 | 0x08003608–0x08003620 写结构 +0x59；0x08003E78/3E8E 送 RT31 |
| 刹车 | ID 0x728，byte[3] bit7 | ID 分支 0x48A+0x29E；0x08003980–0x08003992 写 +0x5A；RT32 |
| 左转向灯 | ID 0x392，byte[1] bit3 | 0x08003734–0x08003768 写 +0x5B；RT33 |
| 右转向灯 | ID 0x392，byte[1] bit4 | 0x0800376A–0x080037A0 写 +0x5C；RT34 |

左右转向灯均为输入为 1 时立即置 1 并清零计数，输入连续 5 次为 0 后才清状态并重置计数。因此固件输出并不是原始位的逐帧直通。内部模型使用 `va3_indicator_hold` 保留该处理，初始状态与日志缺口后保持未知，直到证据足够；该研究模型不宣称还原全部初始化/外部写入和超时行为，禁止直接导出普通 DBC。
