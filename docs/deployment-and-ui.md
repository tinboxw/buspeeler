# 极简部署、技术选型与可视化工作台

状态：首版代码已实施，实机验收待完成。实际运行方式与验证边界见[运行、开发与验收](development.md)。日期：2026-09-22。

已确认需求：**Windows/Linux 都要一键运行，并支持可视化页面操作。** 本文细化[项目架构](architecture.md)中的部署形态、技术栈和首版目标；信号证据、listen-only、独立验证与安全控制规则继续以架构文档为准。

已确认首版硬件品牌：**周立功、创芯科技**。已确认型号名称为 CANalyst-II、周立功 USBCAN2，具体硬件变体和驱动版本仍待核验。

## 1. 产品交付目标

用户拿到与系统匹配的发布包，完成首次安装或解压后，从一个入口启动，自动打开浏览器，即可完成“采集或导入 → 查看报文 → 操作标注 → 比较候选 → 验证 → 导出”。已安装应用后，日常使用不需要命令行、编写脚本或手工编辑配置。

“极简部署”在本项目中的验收定义：

- 一个发布包、一个启动入口、一个应用数据目录，不要求分别启动前端、后端或分析服务。
- 用户不安装 Python、Node.js、编译器、Docker、数据库服务器或消息队列；应用自身运行环境和页面资源随包提供。
- 默认本机使用，所有核心功能可离线运行，不依赖云账户、CDN、在线授权服务或外部 API。
- Windows/Linux 的工作流程、项目格式、算法与验证规则一致；分别提供原生发布包。
- 没接硬件时可以导入日志、完成分析和查看演示；演示与实车证据必须醒目区分。
- 首次硬件驱动/系统权限配置可以需要管理员介入，后续采集和分析尽量使用普通用户权限。此项不能被“免环境”宣传掩盖。

一键启动是用户操作约束，不要求所有模块共用一个进程，也不要求把所有库压成一个可执行文件。浏览器、操作系统与支持列表内的 CAN 驱动属于平台前提。

## 2. 推荐技术选型与取舍

### 2.1 推荐组合

| 层次 | 首选 | 原因与约束 |
| --- | --- | --- |
| 页面 | Vue 3 + TypeScript + Vite | 实现多视图工作台；构建后以静态文件随包提供，不要求用户安装 Node.js |
| 表格/表单/向导 | Element Plus | 复用成熟交互组件；位布局和时间标注按领域需求实现，不另搭低代码系统 |
| 波形/热图/误差图 | Apache ECharts | 统一图表方案；长日志先在后端按窗口聚合，不把全部样本交给浏览器 |
| API 与应用入口 | Python + FastAPI + Uvicorn | 分析和 DBC 生态直接复用；同一个应用提供页面、API、任务管理和下载 |
| 分析计算 | Python + NumPy；需要时增加 SciPy | 特征、候选、回归和验证在同一语言内实现；先实测再优化热点 |
| DBC | cantools | 复用导入导出与格式处理；语义与发布门槛由领域层控制 |
| 采集 | C++17 独立受管进程 | 将接收、持久化和设备故障处理与页面/分析计算隔离 |
| 串口参考 | Python + pySerial，由本机应用管理 | 接入用户已有 EST 工具，原文与时间戳先保存；协议版本匹配后自动标注，不要求浏览器直接访问串口 |
| 本地索引/业务状态 | SQLite + Python sqlite3 | 无数据库服务；主应用作为业务数据唯一写入方 |
| 原始记录/报告 | 分块文件 + JSON 清单 | 适合流式记录、哈希追溯和项目归档；不把所有 payload 塞入事务库 |
| 发行 | PyInstaller onedir + 预编译 C++ 程序 + 前端构建结果 | 运行环境一同分发；分别验证系统与架构组合 |

以上为工程建议，不是已完成的选型验证。依赖版本由实施阶段锁定，开发环境与发行环境使用相同锁文件；不在此阶段增加依赖或生成空工程。

### 2.2 为什么当前不选其他主架构

| 方案 | 优点 | 当前取舍 |
| --- | --- | --- |
| 推荐：Python 应用 + C++ 采集 + Web 页面 | 复用 NumPy/cantools，领域逻辑与分析集中，页面跨平台 | 接受发布包包含运行时，先证明打包可靠性 |
| Go 服务 + Python 分析 + C++ 采集 | Go 服务发行便利 | Python 仍需携带，多出服务与数据契约；现阶段收益不足，不新增 Go 层 |
| 全 C++ + Web 或 Qt | 可以集中原生实现 | 需要重新评估算法及 DBC 库，增加验证成本；当前不为“看起来更单一”重写成熟能力 |
| Electron/Tauri 外壳 | 独立窗口与原生桌面入口 | 系统浏览器已满足页面要求，首版暂不增加桌面容器及其发行链 |
| Docker Compose | 开发部署可复现 | Windows 需额外运行环境，USB/驱动/权限接入更复杂，不作为面向用户的默认交付 |

未来只有测量结果证明现方案无法满足启动、内存、稳定性或硬件需求时才重新决策；跨平台打包困难应在 P0 暴露，不能开发完再交给用户手动装依赖。

## 3. 跨平台范围与硬件边界

| 平台 | 页面与离线分析目标 | 实机采集目标 | 发布前必须确定 |
| --- | --- | --- | --- |
| Windows x64 | 同一工作台、导入、分析、验证、导出 | C++ 分别对接周立功与创芯科技 SDK | 受支持 Windows 版本、型号、驱动/SDK 版本与再分发权限 |
| Linux x86_64 | 同上 | 原生 SocketCAN 或两家设备的官方 Linux SDK/驱动 | 发行版/系统库基线、控制器/适配器、权限与监听能力 |
| Linux ARM64 / RK3568 | 同源构建目标，待设备确定后安排验证 | 原生 SocketCAN；USB 设备需另核验 ARM64 SDK/驱动 | 板卡镜像、系统库、硬件时间戳与 FD；x64 库不能直接复用 |

Windows/Linux 是确认的产品目标；首轮目标基线为 Windows 11 x64 与 Ubuntu 22.04 x64，真实系统验收另行记录。x64 两端作为先行打包验证组合，不能由此宣称 ARM64 已支持。若首测设备确定为 RK3568，则其实际镜像必须加入 P0，而非等到产品发布后补测。

**应用跨平台与采集硬件跨平台分别验收。** 首版必须覆盖两家适配，每家至少选择一个明确型号，逐项验收其 Windows/Linux 组合。仅某组合通过就只声明该组合可用；只有离线分析通过时，明确标作阶段性离线版本。目标组合若无官方支持，需要换选型号或重新确认范围，不能用不安全模式迁就。

采集适配层只定义当前真实需要的能力：枚举设备、查询能力、打开专用通道、确认监听模式、接收帧、查询质量/状态、停止。首版设 SocketCAN、周立功和创芯科技三个后端，不建设动态插件市场或承诺支持两家所有 USB-CAN。原始帧、时钟和质量字段保持相同语义；厂商未提供的元数据保持未知。

用户插入设备后，页面显示“设备可见 / 驱动缺失 / 不支持 FD / 无法确认监听 / 被其他程序占用”等具体状态。SDK 名称包含 silent 或 listen 并不自动构成安全证明，必须结合文档与台架证据确认。安装驱动不能解决的监听限制必须阻断采集。

### 3.1 两家设备的适配决策

周立功的 [USBCANFD 官方产品页](https://www.zlg.cn/can/can/product/id/223.html)说明该系列提供 Windows/Linux 支持和二次开发库；这不证明任一具体版本支持 SocketCAN 或所需监听回读。创芯科技的 [CANFD 官方产品说明](https://www.cxcan.com/h-col-131.html)区分常规版与 Linux 版，且[官方资料下载](https://www.cxcan.com/h-col-114.html)按型号分发资料。因此选型记录必须包含完整型号和版本，不能只写品牌。

| 品牌/路径 | 后端策略 | 当前明确程度 |
| --- | --- | --- |
| 周立功 | 以该型号官方 SDK/头文件为准；旧 ControlCAN 系列与新接口是否需要分别适配，在样机阶段决定 | 品牌确认；型号、Classic/FD、平台架构、监听及时间戳待核验 |
| 创芯科技 | 使用创芯提供的匹配库；即使声称接口兼容，也独立核验结构布局、句柄、时间单位和错误语义 | 品牌确认；常规/Linux 版本、CAN/CAN FD 与监听能力待核验 |
| Linux 原生 CAN | 设备确实暴露受支持的 CAN 网络接口时用 SocketCAN | 不由“支持 Linux”或存在 .so 库推断 |

不同厂商可能分发同名 DLL/.so，分别置于厂商专属目录，通过受管子进程按可信绝对路径加载；不把两个 SDK 混入同一搜索目录，不写系统目录或全局 PATH。依赖 DLL 的加载范围也要限制在该厂商目录及可信系统目录。首版不承诺两家混插并行采集，但切换设备不得残留旧库、占用句柄或错误的设备索引。

支持表以“厂商 + 完整型号/硬件版本 + 固件 + OS/架构 + 驱动/SDK 版本”为键，分别保存 CAN/FD、通道、监听、BRS/ESI、时间戳精度、溢出统计、热插拔、再分发许可与台架证据。不能用一次 Classic CAN 成功覆盖 CAN FD，不能用厂商宣传吞吐代替本应用实测。

## 4. 一个入口内的运行架构

```text
系统浏览器：Vue 工作台
           │ 同源 HTTP API；进度先采用有限频率轮询
           ▼
buspeeler：Python 应用入口
  ├─ 静态页面 + API + 领域规则
  ├─ SQLite 状态、任务调度、进程管理
  ├─ 受管分析子进程（默认同时 1 个重计算任务）
  └─ 受管 C++ 采集子进程（SocketCAN / 周立功 / 创芯科技）
           │
           ▼
本机数据目录：项目索引、原始分块、证据、发布包、日志
```

这些模块属于一个产品，用户不单独安装、启动或配端口。应用对外只监听一个本机端口；内部优先使用受管管道和文件，不增加内部 HTTP 服务、Redis、Celery 或消息中间件。

### 4.1 进程与任务模型

- API 只负责校验、排队和查询，不在请求线程中解析大文件或执行候选搜索。单实例启动，重复点击唤起已有实例页面，不能开出多个 SQLite 写入者。
- 任务状态为 queued/running/cancelling/succeeded/failed/interrupted/cancelled，与信号验证状态完全独立。“任务完成”不表示“信号验证通过”。
- 每个任务绑定项目、输入哈希、定义修订和参数。worker 输出临时结果；主应用校验后提交数据库引用。输入已变时旧结果不得覆盖新版本。
- 默认一个重分析 worker；采集可以并行，但采集优先。采用分块读取、有界缓冲和资源预算，预算不足时排队分析，不能牺牲原始记录完整性。
- 取消是可见状态；worker 在安全分块边界停止。崩溃/重启后未完成任务标作 interrupted，可基于相同输入重跑；首版不承诺任意算法断点续算。
- 采集器直接记录原始分块，只向主程序传递摘要和状态。页面刷新、分页和曲线渲染不进入逐帧持久化路径。

### 4.2 采集、页面与程序退出

关闭或刷新浏览器不停止采集；重新打开页面能看到真实会话和任务状态。页面提供“停止采集”和“退出应用”两个明确动作，退出时先完成受控停止与日志封口。

主进程异常退出时，采集子进程必须通过父进程失联检测结束并封口，不能留下一直写盘的孤儿；恢复时标出不完整尾块。驱动拔插或监听条件失效导致当前会话失败/中断，不自动重新打开接口或继续原验证区间。

初版采用短轮询传递进度和实时摘要，降低 WebSocket 重连与并发复杂度；如实测不能满足刷新预算，再单独评估推送。不要逐帧 HTTP 请求或将全量总线流量广播给浏览器。

## 5. 发布、启动、数据与更新

### 5.1 发布包

选用 onedir：一个目录包含入口、运行时、分析库、采集器、页面、许可证和版本清单，再封装为 Windows 安装包/便携压缩包、Linux 压缩包。安装形态先选一种做正式通道，其余按需求增加，不同时维护多套安装器。

[PyInstaller 官方说明](https://pyinstaller.org/en/stable/operating-mode.html)明确其可携带 Python 运行时，也说明发行包与系统相关；onefile 会在运行时解包。因此优先 onedir，不以单文件数量作为部署质量指标。系统库、驱动和浏览器仍需符合支持矩阵，Linux 包不能无条件适配所有发行版。

前端在构建阶段产生静态资源，由应用提供服务；用户端不运行 Vite 开发服务，见 [Vite 静态部署说明](https://vite.dev/guide/static-deploy.html)。所有脚本、样式、图标和字体随包提供，无 CDN 依赖。外部参考链接仅供阅读，不影响离线业务流程。

Windows 提供一个可双击入口和启动错误提示；Linux 桌面提供经过目标桌面环境验证的启动入口，无桌面设备保留等价单命令入口。系统首次安装、执行权限或安全软件提示属于需真实测试的发行体验，不承诺零系统确认。签名、许可证与依赖清单在发行阶段落实。

### 5.2 启动行为

1. 检查已有实例、应用数据目录写权限、磁盘空间及数据格式版本。
2. 在 loopback 上绑定可用端口，再启动健康检查；端口冲突可选择空闲端口，不能终止其他程序。
3. 检查必需应用组件；CAN 驱动缺失只影响采集，不能阻止离线工作台启动。
4. 服务就绪后打开系统浏览器。打开失败时显示可复制地址；页面未就绪前不跳出白屏。
5. 首次进入显示“新建项目 / 打开项目 / 查看演示”，接入检查放在用户选择实机采集之后。

默认只绑定本机，首版不要求用户配置公网、证书或反向代理。若以后需要另一台电脑访问设备，应另增显式局域网模式，配套认证、传输保护和端口访问限制；不得为了方便默认监听全部网卡。

本机接口仍校验 Host/Origin，使用应用启动会话凭证保护变更操作，不把 loopback 当成无条件可信。文件接口仅访问该项目允许的路径；上传、压缩包解包、日志/DBC 解析有大小和路径约束。浏览器不能绕过后端发布与监听门槛。

### 5.3 数据与升级

程序文件和用户数据分离；默认使用平台应用数据位置，首次界面允许选择自有数据目录。目录建议如下，路径由页面显示和打开，不要求用户手改配置：

```text
<data-root>/
  app.sqlite            项目索引、任务、定义修订、审核及设置
  projects/<id>/
    raw/                原始日志与采集分块
    reference/          参考测量和标签
    derived/            可重建的索引、特征与图表缓存
    evidence/           验证记录与报告
    releases/           不可变发布包
  logs/                 应用诊断日志
```

SQLite 只在本机磁盘使用，重分析产物先写文件、主程序短事务登记，不让大量原始帧占用业务写锁。SQLite 适合本地应用的选择依据见[官方适用场景说明](https://www.sqlite.org/whentouse.html)。不通过网络共享目录让两台应用同时打开同一数据库。

页面支持项目归档导入/导出，包括必要证据与校验清单；只下载 DBC 不等于完整项目备份。运行中的归档通过一致性快照完成，不直接复制正在写入的数据库文件。

升级前在页面停采集/完成任务并备份，替换程序包后执行版本化迁移。迁移失败保留可诊断状态和备份；旧程序不能强开新 schema，回退须恢复兼容的数据备份。首版不增加后台在线自动更新或自动删除原始日志。

## 6. 可视化导航与页面责任

全局入口保持少量，工作内容围绕一个车辆/总线范围明确的项目组织。

```text
项目首页
  ├─ 新建 / 打开 / 导入归档 / 演示
  └─ 当前项目
       ├─ 数据：采集、日志导入、参考文件、质量检查
       ├─ 分析：消息列表、位布局、波形、标签、候选比较
       ├─ 验证：实验向导、独立会话、指标、失败与审核
       └─ 协议：信号定义、版本、发布检查、导出与撤销
设备与设置：驱动诊断、数据目录、应用状态、备份与退出
```

| 页面 | 核心操作 | 必须显示的结果与恢复路径 |
| --- | --- | --- |
| 项目首页 | 明确车辆、接入网络与目标信号；打开项目 | 未知信息可保留，演示标签不消失，最近任务状态可恢复 |
| 数据 | 枚举设备、选择通道和参数、开始/停止；拖入日志/参考 | 监听确认、帧率、时间来源、可用磁盘、丢帧/错误；失败给下一步而非空白 |
| 分析 | 过滤消息、刷选时间、查看变化位、选候选、叠加参考、打标签 | 原始字节与解码解释同屏；多个等价候选保留；显示采样缺口 |
| 验证 | 选择实验模板、采样/导入标签、分配独立会话、运行与审核 | 阈值、输入版本、已覆盖/未覆盖条件、失败样本、重新采样入口 |
| 协议 | 编辑候选定义、查看修订差异、运行发布检查、导出/撤销 | 候选与正式版本区分；阻断项链接到证据；不能直接下拉改成已验证 |
| 设置 | 检查设备/权限、选择数据位置、归档、诊断与退出 | 软件版本、硬件支持情况、任务状态；不让普通用户输入 shell 命令 |

设备参数配置在首版采用“首次驱动/权限准备 + 页面能力检查与选择”。两家 SDK 后端由适配器受控配置并打开专用通道；SocketCAN 后端首版使用预配置的专用接口，页面回读检查。Linux 需要管理员准备权限和监听配置时，给明确的一次性安装说明。需要修改内核网络配置的操作不得把整个 Web 服务提升为管理员/root；若以后增加页面配置助手，只允许有限设备操作，不提供任意命令执行。

## 7. 长日志与交互性能设计

原始数据按分块流式读取；后端建立消息/时间索引，页面按所选消息和时间窗口请求。实时页面只显示有界摘要，历史曲线使用保留极值/事件的抽样视图，显示其抽样方式；验证算法始终读取规定精度的原始数据，不能对显示用抽样曲线计算验收结论。

首版建议设定以下可测预算，在 P0 固化测试机、样例日志、参数和测量方法后作为门槛。以下均为目标，不是当前性能证据：

| 项目 | 首轮目标/方法 |
| --- | --- |
| 冷启动 | 两端发布包在基准机上 10 秒内达到页面可操作；单独记录系统安全扫描等首启开销 |
| 样例项目 | 100 万帧、含 FD/扩展帧/标签/缺口；索引完成后常用消息与时间窗口查询 P95 不超过 1 秒 |
| 图表 | 默认每曲线每窗口不超过 5,000 个显示点，可按需缩放取更细数据，最多同时展示 8 条曲线作为首轮预算 |
| 实时状态 | 帧率与设备状态目标每秒更新 2 次，不承诺逐帧动画；关键失败立即写入后端状态并在下一次查询显示 |
| 后台计算 | 重任务运行时仍能访问页面、查看进度并提交取消；不以候选搜索总时长阻塞整个应用 |
| 采集容量 | 按实际硬件、通道数、Classic/FD 帧分布和目标速率持续测量，记录各层丢帧和资源使用；数值待设备选型 |

若 100 万帧仍触发全量载入内存、页面假死或表格一次渲染全部记录，视为设计未达标。超过首版预算的输入应给出估算、排队或明确限制，不能直接失去响应；硬件采集吞吐不能从离线浏览性能推算。

## 8. 首版实现目标与顺序

保留架构文档 P0–P4 编号，调整 P0/P1 的完成定义：部署与页面闭环是首版前提，不能只交付命令行算法。

### P0：先证明能交付，再铺开算法

1. 在 Windows/Linux 无开发工具的干净环境中，离线启动已打包应用，打开自带页面。
2. 页面完成合成日志导入、消息表/曲线查看、一个后台任务和演示导出；演示不推进任何实车验证状态。
3. 验证 NumPy/cantools、页面资源、子进程、中文/空格路径、端口占用、只读目录、退出与重启。
4. 确定周立功与创芯科技各自样机，逐一核验 Windows/Linux 组合、监听、FD 能力、时钟和异常，并测试切换厂商不会加载错库；采集断连不会拖垮离线应用。
5. 固化支持矩阵、资源预算、打包命令、许可证清单和重复执行的发布冒烟检查。

P0 打包验证失败时先解决分发路线；不得先堆功能，再要求用户安装 Python 或改用 Docker。

### P1：用户可独立完成的最小可视化闭环

必做范围：项目与会话管理；一种明确文法的 candump 日志导入及自有采集格式；参考 CSV/操作标签导入；消息/位/波形查看；基础候选发现与人工修订；门、灯等状态实验向导；独立会话验证；按总线导出正式 DBC 包；版本撤销、任务恢复、项目归档与错误诊断。

已有 EST 工具接入首版参考路径：增加串口选择、原始流/协议匹配预览、CAN/串口同步记录、自动状态标签及同源证据提示。以更正后的 EST580 内部版手册的 39 字段 RT 为基线，具体 profile 经过实际串口样本核对，见 [EST 参考与固件评估](est580-reference-and-firmware.md)。IDA/LLVM 等分析工具仅用于离线研发，不进入用户发布包。

导入器声明支持的具体日志语法、时间精度和 FD 标志处理，未知行返回行号/原因，不能声称兼容所有 .log 文件。首版无需同时支持 BLF、ASC、MDF 等全部格式；格式扩展单独验收。

跨平台验收脚本对应同一用户旅程：

```text
启动应用 → 新建项目 → 导入或采集 → 查看质量
→ 标注一次操作 → 比较并保存候选 → 选择另一独立会话
→ 运行验证 → 查看失败或审核通过 → 发布并下载 → 重启后再次打开
```

任何一步必须通过命令行补救才能继续，都不能算页面闭环完成。采集前的驱动安装/设备权限属于明确列出的首次环境准备，不应重复出现在日常流程中。

### P2–P4：在同一工作台扩展

P2 增加连续物理量参考、时间映射、factor/offset 拟合与残差展示；P3 增加模板指纹、复用、校验和 ISO-TP 视图；P4 扩展消费工具与控制系统适配，按真实需求增加远程访问。第一版不包含移动端专用界面、多用户角色体系、云服务、插件市场、主动诊断或未知报文发送。

## 9. 验收证据与尚待决定事项

正式发行至少留存两端的干净环境启动记录、完整页面流程结果、代表性数据性能记录、设备监听台架证据，以及错误路径结果。页面刷新、后台崩溃、应用重启、磁盘不足、驱动拔插、非法 DBC、输入变更和发布阻断均属于验收范围。

不承诺覆盖全部 Windows/Linux 版本。品牌已确定为周立功、创芯科技；当前待确认的是两家完整型号/硬件版本、Linux 实际设备/镜像、最低系统版本、代表性吞吐与首测参考源。上述选择决定支持矩阵；技术栈建议先通过 P0 样机验证，再作为开发基线锁定。

本文只更新设计，没有创建应用工程、安装依赖或修改机器驱动。页面草图用于功能与布局讨论，后续开发前再确认具体视觉方案。
