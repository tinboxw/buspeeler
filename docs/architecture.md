# buspeeler 项目架构与实施路线

状态：设计提案，待实现与验证。整理日期：2026-09-22。

本文整理“跨车型 CAN/CAN FD 信号逆向分析与 DBC 自动生成系统”方案，作为项目级设计基线。编写时仓库只有 LICENSE，没有代码、构建系统或既有架构文档；下述模块、数据字段及门槛均为拟议设计，不是已经实现的能力。

补充约束：Windows/Linux 都应一键启动，通过可视化页面完成核心流程。具体部署与交互设计见[极简部署、技术选型与可视化工作台](deployment-and-ui.md)。本篇负责信号与证据规则，配套文档负责产品形态和实施验收，两者共同构成设计基线。

## 1. 项目目标与能力边界

在自有或获授权车辆的可访问 CAN/CAN FD 网络上，可靠保留原始通信，自动发现信号候选，通过已有定义、引导操作和参考测量确认解码规则，最终输出带车型版本、使用条件和验证证据的 DBC。

核心流程是：**通用采集 + 已有协议匹配 + 候选发现 + 引导标定 + 独立验证 + DBC 导出**。

| 能力 | 目标 | 边界 |
| --- | --- | --- |
| 跨车型采集 | 接收接入网络上的标准/扩展帧、Classical CAN/CAN FD | 依赖物理层、控制器、驱动、速率及正确接入点 |
| 自动发现 | 提出位范围、大小端、符号、类型和复用候选 | 排序与相关性不构成正确性证明 |
| 语义识别 | 确认门、灯、挡位等状态或连续物理量 | 需要可辨识工况、参考值或可信协议依据 |
| 解码规则恢复 | 确认 factor、offset、单位、枚举及有效条件 | 原始日志可能容许多个等价解释 |
| DBC 发布 | 导出已验证信号集合及依赖定义 | 部分信号正确不等于整车协议恢复 |
| 下游接入 | 提供带有效性、时效和版本的解码结果 | 不因“已发布”自动获得车辆控制资格 |

**不承诺无参考信息即可恢复任意车型完整原厂 DBC。** 原厂命名、未激励高位、未观测枚举、复用分支和软件版本差异可能无法从日志确定。例如恒为零的高 4 位，不能证明一个字段是 12 位而不是 16 位；相同 raw 序列也可能对应速度、压力或转速等不同物理量。

OBD 接口可连接不代表内部车身广播均可见。接入检查必须区分“无流量”“参数不匹配”“该接入点不可见”“当前工况未出现”和“定义未知”；没有证据时不得断言车辆不存在目标信号，也不得自动绕过网关限制。

首版不包含主动发报探测、控制报文注入、密钥恢复、认证绕过或完整诊断控制。CAN XL、其他物理层和复杂应用协议不作为首版兼容承诺。

## 2. 总体架构与模块职责

采集端以可靠记录为主，分析端以可解释推断和证据管理为主。默认将两者打包为本机应用，采用浏览器工作台，先做单机闭环，不预设云服务、微服务或端到端大模型。Linux 原生网络接口使用 SocketCAN；周立功和创芯科技 USB 设备按具体型号在 Windows/Linux 使用适配的官方 SDK 或已验证的 SocketCAN 驱动。页面和分析模型共用，不将“支持 Linux”等同于“提供 SocketCAN”。

```text
车辆可访问 CAN / CAN FD
          │  隔离接口 + 控制器 listen-only
          ▼
C++ 被动采集器（SocketCAN / 周立功 SDK / 创芯科技 SDK）
          │  原始帧、时间戳、配置与质量事件
          ▼
不可变原始记录 ─────────── 操作标签 / 外部参考测量
          │                              │
          ▼                              │
预处理与已有 DBC / 车型模板匹配            │
          │                              │
          ▼                              ▼
报文/位特征 → 结构候选 → 语义对照与时间对齐标定
                          │
                          ▼
                  内部信号模型与证据
                          │
                          ▼
                  独立数据验证 + 审核
                          │
                          ▼
           按总线导出 DBC + manifest + 验证报告
                          │
                          ▼
             带有效性门槛的 C++ / ROS / Pilot 适配
```

| 模块 | 输入 | 输出与责任 |
| --- | --- | --- |
| 采集器 | 专用接口与明确的会话配置 | 原始记录、监听状态、质量事件；不执行候选算法或发送业务报文 |
| 预处理 | 原始记录、参考记录 | 可追溯的分组、时间映射和质量掩码；不改写原始字节 |
| 匹配与发现 | 报文画像、已有模板 | 模板建议、候选集合、未决歧义 |
| 标定向导 | 候选、标签、参考值 | 实验步骤、拟合参数、反例与覆盖范围 |
| 验证与审核 | 冻结的定义和独立会话 | 按信号的通过/失败/证据不足结果及状态迁移 |
| 导出器 | 获准发布的模型快照 | 可重现的 DBC 发布包或明确的阻断原因 |
| 下游适配 | 发布包与运行帧 | 值、有效性、时效、验证版本；执行运行时使用条件 |

用户从统一页面执行采集、分析、标定、验证与导出；内部采用库函数、受管子进程与文件契约分离。命令行保留给自动化和诊断，不作为普通用户完成流程的前提。原始记录、分析结果、发布包分别版本化；任何结果都能追溯到源文件哈希、记录区间、工具版本和参数。算法可以给建议，不能自行跨越验证发布门槛。

## 3. C++ / SocketCAN 被动采集层

### 3.1 接入与启动门槛

默认只读。**程序不调用发送接口不等于硬件真正被动监听**；必须在控制器层启用并回读确认 `listen-only`。SocketCAN 的控制器模式与 Classic/FD 帧接口以 [Linux SocketCAN 文档](https://docs.kernel.org/networking/can.html)为准。

启动流程拟定为：

1. 选择专用采集通道，记录接入点、适配器、驱动、固件、终端电阻安排及已知总线参数。
2. 检查控制器/驱动对 CAN FD、监听模式和时间戳的实际支持；FD 仲裁阶段与数据阶段参数分别记录。
3. 由独立配置步骤设置已确认的采集参数，采集进程只检查配置。不得自动停启承担其他业务的接口。
4. 回读接口配置、监听模式和状态；不支持、配置失败或无法确认时停止实车采集，不回退普通收发模式。
5. 运行期间观察配置变化、接口重启和质量事件；失去监听保证即停止会话并标记受影响区间。

未知速率仅允许明确的被动识别流程；识别失败报告原因，不主动发报探测。隔离、电气兼容性、接地、线束和终端匹配需要按实际硬件验证；不能在已有总线上随意增加终端电阻。只有监听节点的台架可能缺少正常通信所需的其他节点，不能用切回主动模式“修复”采集。

### 3.2 接收与持久化

采集器拟采用 C++17 和 `CAN_RAW`，按实际接收结构区分 `can_frame` 与 `canfd_frame`；FD 通道显式启用对应接收能力。保留标准/扩展帧标志、FD 的 BRS/ESI 和接收来源，错误通知及远程帧单独记录，不作为普通 payload 分析。

接收路径只做必要校验、序号赋值和入队，持久化线程按批次写入分块文件。队列必须有界；磁盘满、写失败、缓冲区溢出、设备断开都产生可见质量事件。无法可靠持久化时结束或暂停会话，不能静默丢弃后声称采集完整。

优先使用硬件时间戳，不能获得时保留可用的软件时间戳并注明来源。记录设备时钟域及其到会话时钟的映射；不得将未知精度表示为零误差。多通道对齐能力以实际适配器测试为准。

丢帧统计分别记录驱动/控制器、socket、应用队列及磁盘路径能提供的证据。观测到零次溢出不证明链路绝对无丢帧；未知统计项保持未知。日志关闭时保存计数、时间范围、文件哈希和结束原因；异常退出后的恢复必须能识别未完整写入的尾部。

`vcan` 和录制日志用于软件验证，实物台架另外确认总线侧没有采集器发送、ACK 或主动错误帧行为。虚拟接口测试不能代替硬件监听验证。

### 3.3 周立功与创芯科技跨平台适配

Windows 由 C++ 设备适配层对接周立功或创芯科技 SDK；Linux 对这两家设备也需核对具体型号的 SDK/驱动形态，不强制转换为 SocketCAN。第 3.1–3.2 节的 SocketCAN 调用仅适用于该后端，被动性、数据质量与停止原则适用于所有后端，统一输出第 4 节的数据模型。

设备枚举、Classic/FD、监听模式确认、时间戳和溢出统计必须逐型号核验；不支持项明确标记，不以接口同名推断语义相同。原生驱动与 SDK 的授权、架构和再分发限制属于选型门槛。两家同名动态库分别存放、按可信绝对路径在各自采集子进程加载，不覆盖系统 DLL 或修改全局搜索路径。

首版适配范围已确定为周立功和创芯科技，每家至少选择一个明确型号，分别核验 Windows/Linux 组合；目前具体型号待确认，能力未知。首版完整交付须覆盖两家适配及两种系统的实机采集，不能只验证其中一家后标作整体完成。没有驱动或没有可确认的硬件监听保证时禁用实机采集，日志导入与离线分析仍可使用。不得以页面可打开或模拟数据可回放代替实机采集验收。

## 4. 原始数据模型与存储

所有模型有 `schema_version`。原始记录不可被清洗结果覆盖；连续重复帧不得去重，因为重复次数和间隔是周期与保持状态的证据。硬件未提供的字段使用 `null/unknown`，并记录原因。

### 4.1 会话、帧与质量事件

| 对象 | 建议字段 | 约束 |
| --- | --- | --- |
| 会话 | `session_id`、车辆匿名标识、车型/年款/配置、已知 ECU 软件版本、日期、接入点、操作者 | 未知版本不得凭车型名称补齐 |
| 通道 | `channel_id`、接口/适配器映射、物理总线、bitrate、data bitrate、FD 配置、监听回读结果 | 同名 can0 在不同设备/会话中不自动视为相同网络 |
| 时间 | 原始时间戳、单位、时钟域、来源、精度或不确定度、会话时间映射版本 | 保留时钟跳变和漂移证据 |
| 帧身份 | `session_id`、`record_seq`、`channel_id`、`arbitration_id`、`is_extended`、`is_fd`、`frame_kind` | 仲裁 ID 不混入 SocketCAN 标志；错误通知保留其原始错误标记，不伪装仲裁 ID |
| 帧数据 | `payload_length`、原始 `payload`、可用时的 `raw_dlc`、`brs`、`esi`、接收来源 | 实际字节数与 DLC 编码分离；FD 不采用固定 8 字节模型；RTR 无业务载荷 |
| 质量事件 | 事件类型、开始/结束时间或记录区间、计数来源、累计/增量语义、严重度 | 丢帧、截断、错误、时间异常、配置变化可关联到分析区间 |
| 文件清单 | 路径、格式版本、哈希、大小、首尾序号、完成状态 | 派生结果引用清单，避免只引用易变路径 |

基础消息身份键为 `session + channel + arbitration_id + is_extended + is_fd`，仅普通数据帧进入字段分析。同身份先检查长度分布，再按实际长度拆分分析视图；可变长度原因未知时不得补零拼成固定消息。跨会话合并需要显式车辆、总线及版本映射。

### 4.2 标签、参考值与派生结果

- 操作标签：实验 ID、开始/结束时间、时钟域、目标操作、实际观察状态、标注者、时间误差与备注。操作意图和执行结果分别记录。
- 参考测量：参考源 ID、物理量定义、单位、原始时间与数值、精度/校准记录、有效性和采样间隔。人工标签不是无误差真值。
- 分析运行：输入哈希、筛选区间、质量掩码、算法/工具版本、随机种子（适用时）、参数、候选排序及失败原因。
- 验证记录：定义版本、独立会话、预先确定的阈值、指标、覆盖范围、反例、审核结果和证据链接。

首版优先采用已有原始日志格式与配套 JSON 元数据清单，不凭空设计复杂二进制协议。若格式无法保存某项元数据，必须在配套文件中补存或声明丢失；文本日志导入不能虚构硬件时间戳、DLC 或丢帧统计。SQLite 保存索引、候选与审核状态；数据量证明有必要后再增加 Parquet 等派生分析缓存。

## 5. 已有 DBC 与车型模板匹配

已知车型先检索定义，未知车型直接进入发现流程，两者最终使用同一验证门槛。

模板绑定品牌/平台、车型、年款、配置、接入总线、已知 ECU 软件版本、协议来源/许可证、模板版本和验证证据。匹配特征包括 ID 集合、帧类型、长度分布、周期分布、稳定字段及已知信号的统计特征。

匹配结果输出候选模板、支持证据、冲突项、缺失项及采样覆盖不足项。指纹只用于缩小搜索范围；ID 与长度相同、排名第一或来源可信，都不能直接证明适用于当前车辆。导入 DBC 的信号在当前适用范围中仍需确认，不能继承其他车型的发布资格。

版本差异按信号处理：可复用部分重新验证，冲突部分保留为新候选；未观测消息与明确不匹配分别呈现。不同通道的同 ID 绝不默认合并。模板也不得自动执行其附带脚本或触发车辆通信。

## 6. 报文级与位级特征分析

先建立消息画像，再产生结构候选。长度、复用分支和会话边界不能混算；明显丢帧或时间异常区间需单独标记。

| 层级 | 特征 | 用途 |
| --- | --- | --- |
| 报文 | 数量、长度分布、周期中位数、抖动、突发、出现/消失时间 | 判断周期/事件型消息及可见性 |
| 位 | 取 1 比例、熵、翻转率、相邻位联合变化 | 定位变化区域及边界假设 |
| 字节/字段 | 唯一值数、差分、模递增、连续性、状态驻留时长 | 区分枚举、连续量、计数器等假设 |
| 事件 | 相对标签的延迟、变化一致性、对照区间误报 | 提出语义关联，发现混淆候选 |

对于分组内 N 个有效观测，第 j 位翻转率为：

```text
F[j] = sum(bit[j,k+1] != bit[j,k]) / (N - 1)
```

N 小于 2 时结果未知；跨丢帧区间的相邻观测不等于相邻总线帧。翻转率按消息采样计算，不能忽视报文周期差异直接比较不同 ID。

静态位可能是未激励字段，不能直接删作保留位；高熵也可能来自连续量低位、计数器、校验或认证字段，不能直接认定加密。此阶段只输出候选类型与证据，不给未知字段强加业务名称。

## 7. 候选边界、大小端与符号搜索

候选结构至少包含消息身份、实际长度、`start_bit`、`bit_length`、`byte_order`、`signedness` 和复用条件。支持非字节对齐与跨字节字段；先按特征缩小区域，再联合搜索，保留可配置数量的候选及被排除原因。

内部统一采用每字节 bit0 为最低位的 payload 位编号，保存显式位序或可复现提取规则。转换到 DBC 时严格遵守其起始位含义：Intel 起始位指向最低有效位，Motorola 起始位指向最高有效位。沿 Motorola 信号由高位读向低位时，位置规则为：

```text
current % 8 != 0：next = current - 1
current % 8 == 0：next = current + 15
```

因此 Motorola 不能用简单的 `start + length` 判断占位。大小端接口和示意可核对 [cantools Signal 文档](https://cantools.readthedocs.io/en/latest/#cantools.database.can.Signal)。

对长度为 L 的二进制补码候选，先提取无符号值 u，再计算：

```text
u < 2^(L-1) 时：raw = u
否则：          raw = u - 2^L
```

候选评分综合边界特征、取值规律、物理参考误差、有效条件和反例表现；分数用于排序，不作为发布阈值。保留以下歧义：高位未变化导致位宽不唯一、没有负值导致符号不唯一、位移与缩放相互补偿、多个物理量同步变化、不同复用分支混合导致伪连续量。

超出首版提取能力的浮点、BCD、非连续位拼接或特殊编码标记为待支持，不能强行套整数模型。固定测试向量应覆盖跨字节大小端、非对齐、正负边界、FD 长载荷和非法位范围；合成向量只验证提取实现，不证明车辆语义。

## 8. 引导式操作标定

向导按“目标定义 → 安全前提 → 基线 → 操作与保持 → 恢复 → 对照动作 → 复测”组织实验。每次显示当前候选、尚缺证据和能区分候选的下一步操作；允许标记无法执行，不以危险操作补齐覆盖。

| 目标 | 操作/参考设计 | 必须区分的含义 |
| --- | --- | --- |
| 车门 | 停车后分别开关各门，保持、换序、复测；单独操作车内灯作为反例 | 单门/任意门开启、门锁、照明、开门请求 |
| 转向灯 | 左、右、关闭、双闪及实际灯具观察 | 拨杆请求、闪烁相位、执行输出 |
| 雨刷/灯光 | 覆盖可安全执行的挡位和模式，记录实际结果 | 请求状态、实际工作状态、自动模式 |
| 制动状态 | 驻车安全条件下踩下/释放，配合独立状态或位置参考 | 开关、踏板位置、压力、刹车灯、减速度 |
| 挡位 | 具备安全条件时观察实际挡位与挡杆动作 | 挡杆位置、目标挡位、实际挡位 |
| 车速/转角 | 台架或合适封闭场地，同步可靠速度/角度参考 | 仪表车速、轮速、地速；方向盘角、前轮角、角速度 |

改变操作顺序、时长，加入无操作片段、互斥动作与恢复阶段，避免计数或时间趋势伪装成目标信号。标签描述实际观察，不只记录按下按钮的时间。GNSS 地速不自动证明单轮轮速，IMU 横摆角速度不能直接当方向盘角度真值。

首版从门、灯、雨刷等易于安全复测的离散状态开始。OBD/UDS 请求通常涉及发送，不属于默认被动采集；如未来需要诊断参考，应作为独立明确启用、授权且受控的扩展，不能在后台自动开启。

用户已有 EST 工具可作为串口参考源，与原始 CAN 同步记录并自动生成变化标签。已提供固件可通过静态分析形成结构候选；详见 [EST 串口参考标注与固件分析](est580-reference-and-firmware.md)。协议基线采用用户更正后的 EST580 内部版手册及其 39 字段 RT 定义，具体固件的扩展仍需确认；转向单位由用户确认为百分比，R25 表示 25%，方向映射另验。同一固件派生的 CAN 规则与该工具的串口输出属于同源证据，一致性不替代独立语义验证；串口只读也不证明 EST 在车辆侧被动。

## 9. 连续物理量的 factor/offset 与时间对齐拟合

对线性候选，拟合模型为：

```text
y(t + tau) = factor * raw(t) + offset + residual(t)
```

其中 t 是已映射到共同时间基准的 CAN 时间，tau 表示参考序列相对该信号的时间偏差。时钟偏移/漂移与传感器延迟分别记录，不能把所有误差都解释为固定延迟。

建议流程：

1. 在搜索前按采集会话或完整工况划分发现/标定集与锁定的独立验证集，防止相邻帧随机拆分造成泄漏。
2. 检查参考量定义、单位、校准精度和有效区间；建立时钟映射，剔除或标记参考失效、日志缺口及复用不匹配区间。
3. 在合理且事先设定的窗口估计延迟，再拟合 factor/offset；必要时使用稳健回归，但保留异常点及剔除理由。
4. 重采样时记录插值规则和最大容许间隔；连续量不跨缺口插值，离散状态不能线性插值。
5. 检查样本覆盖、参数可辨识性、残差与参考误差。常值/窄范围样本不足以确认比例；高相关不证明语义。
6. 冻结候选、时间映射策略和参数，在独立会话复核。验证数据不能用于重新挑选最佳延迟、边界或比例；若回用于调参，须另收独立验证集。

报告 factor、offset、tau、时间不确定度、MAE、RMSE、最大/分位误差、异常比例，以及实际覆盖的范围和动态工况。阈值随目标用途和参考精度预先确定，不统一采用“相关系数大于 0.99”。

饱和、无效码、滤波延迟、非线性、回绕和迟滞分别处理。线性模型不适用时保留未知或特殊模型，不能为了导出 DBC 而伪造线性系数。编码可表示范围、实测观测范围和独立验证范围必须分开存储。

## 10. 多路复用、计数器、校验与 ISO-TP

### 10.1 多路复用

先提出选择器及条件候选，按分支分别分析、标定与验证，再确认分支有效位。共用位段只有在互斥条件下才可重叠；未知选择器值返回未覆盖状态，不能套用最常见分支。嵌套或扩展复用需要内部条件模型与目标 DBC 工具共同支持。

分支信号的验证/发布依赖选择器定义；选择器变更必须使依赖证据失效。不同长度同 ID 可能与复用相关，也可能有其他原因，不凭长度变化直接确认复用。

### 10.2 计数器

检验 `r[k+1] = (r[k] + step) mod 2^n` 等假设，分别分析复位、回绕、暂停、分支切换与重启。结合时间间隔和采集质量解释跳步；既不能把每次跳步认定候选错误，也不能把每次跳步都解释为丢帧。

计数器用于排除伪物理量和辅助质量诊断，不自动成为业务信号或整条链路完整性的证明。

### 10.3 校验、完整性与认证

疑似 checksum/CRC 字段单独建候选，记录参与字节、ID/计数器等可能输入、算法参数、覆盖范围和独立验证结果。高熵不证明 CRC；某段数据匹配也不证明算法唯一或已具备报文生成能力。

“业务字段能解码”和“应用层报文完整性已验证”是两个独立状态。校验规则未知时可以保留研究用解码，但不得声称完整性已验证。CAN 链路差错检测不能替代应用层的新鲜度、真实性或完整性约束。

认证不必然意味着整个 payload 加密。未掌握的认证或加密内容保持未知；DBC 不表达密钥，也不替代认证状态机。安全控制所需完整性/新鲜度条件无法满足时，运行时必须拒绝使用该值。

### 10.4 ISO-TP 与诊断多帧

默认从原始帧离线识别并重组已发生的通信，不把分片控制信息当固定布局业务字段。会话键包括通道、已确认的通信方向/ID 配对与寻址信息；保留组成帧引用、序号、总长度、超时、缺片和重组完成状态。配对或寻址未知时保留候选，不强拼。

重组不完整的数据不能作为完整应用消息解码或标定依据。ISO-TP 重组之后的诊断语义仍需单独定义，DBC 不替代传输层和诊断协议。

在线 ISO-TP 接收可能引入 Flow Control 发送。若后续使用内核 ISO-TP 监听，必须核实禁发流控的模式并保持控制器监听保证；官方 `CAN_ISOTP_LISTEN_MODE` 的含义是接收时不发送 FC 帧，见 [Linux ISO-TP 文档](https://docs.kernel.org/networking/iso15765-2.html)。纯被动观察不能保证获得尚未自然发生的完整诊断交换，不得为补齐数据自动发请求或流控帧。

## 11. 验证状态机与发布门槛

### 11.1 按信号和定义版本维护状态

```text
unknown → candidate → calibrated → validated → published
              ↑            │           │           │
              └── 新歧义/验证失败 ───────┘           │
                                                   ▼
                                                revoked
```

| 状态 | 进入条件 | 可用范围 |
| --- | --- | --- |
| `unknown` 未知 | 尚无可用解释或证据不足 | 保留原始字段 |
| `candidate` 候选 | 自动搜索、模板导入或人工提出结构/语义假设 | 研究分析；不能用于控制 |
| `calibrated` 已标定 | 在标定集确定结构、语义、参数、有效条件与证据 | 准备独立验证；不是正确性承诺 |
| `validated` 独立验证通过 | 冻结定义在独立会话达到预设门槛，歧义已处理，证据经审核 | 限已验证范围；尚未形成发布包 |
| `published` 已发布 | 验证通过并通过全部导出/适用性/依赖门槛 | 按发布清单用于限定场景 |
| `revoked` 已撤销 | 已发布定义出现反例、关键错误或适用性证据失效 | 禁止新使用；保留历史包与原因 |

离散信号的“标定”指枚举、极性、语义与条件确认，不要求虚构连续量拟合。每次迁移记录定义哈希、证据 ID、执行者、审核者、时间和原因；候选分数不能直接推进状态。

定义、选择器、参考校准或时间处理发生影响结果的变化时，创建新修订并从候选/标定重新验证。历史发布包不可改写；已知错误必须撤销，单纯扩大目标范围则产生新适用性记录，不能默许原记录覆盖新车型。重复解码同一日志不属于独立验证。

### 11.2 正式发布必须全部满足的门槛

| 门槛 | 必要证据 | 阻断示例 |
| --- | --- | --- |
| 采集质量 | 接入与监听记录、可用时间范围、丢帧/异常说明 | 关键区间质量未知且影响判断 |
| 结构 | 帧类型/长度/位序合法；活动分支无非法重叠；依赖完整 | 字段越界、复用选择器未确认 |
| 提取实现 | 人工确认或独立生成的已知向量，含大小端、符号与边界 | 只依赖同库编解码回环 |
| 语义 | 操作对照、参考定义、混淆排除证据 | 只证明“随制动一起变化” |
| 数值/枚举 | 独立会话误差、各状态表现、转换时间及预设阈值 | 缺少关键状态，误差超限，验证集被用于调参 |
| 条件与覆盖 | 有效码、复用分支、超时、范围、车辆/软件/总线适用性 | 将未覆盖范围标作已验证 |
| 导出兼容 | 严格重载、结构等价核对、目标工具或独立解码实现回归 | FD/扩展复用等信息被静默丢弃 |
| 可追溯与审核 | 定义/输入/工具哈希、验证报告、授权来源、审核及限制 | 证据不可定位或未决歧义影响目标用途 |

连续量报告误差及覆盖，离散量报告各状态的混淆/误报/漏报与转换时刻误差；采样数和阈值须在验证前按目标任务确定，不能只报告总体准确率。未验证状态和区间明确排除；若会影响目标用途则阻断发布。

严格解析只能证明文件和结构层面的合法性；同一错误定义的编码/解码也可以自洽。部分 DBC 回环仅比较已定义且当前有效的位掩码，不要求未知位、计数器或其他分支逐字节相同。

### 11.3 安全相关使用门槛

**安全相关控制只能使用独立验证通过的信号。** 下游控制接入还必须使用未撤销的已发布版本，并确认实际车辆/总线匹配、值未超时、当前状态在验证范围内、依赖选择器与必要完整性检查有效。独立验证是必要条件，不替代控制系统的风险评估、故障处理、系统验证和实车准入。

运行结果至少包含 `value`、`timestamp`、`valid`、`age`、`invalid_reason`、`verification_status` 和 `profile_version`。未知、超时、未覆盖分支、无效码或撤销不得转换成看似有效的数值零；下游须据无效原因执行自身已验证的降级策略。

## 12. 内部信号模型与 DBC 导出

### 12.1 内部模型是事实源

分析算法只更新结构化定义，不直接拼接 DBC。DBC 是内部模型的兼容导出，不能承载全部验证与使用条件。

| 模型部分 | 建议内容 |
| --- | --- |
| 身份 | `signal_id`、修订、`profile_id`、车型/版本范围、逻辑总线、消息引用 |
| 消息 | 原始仲裁 ID、标准/扩展、Classic/FD、实际长度、周期画像、超时策略 |
| 布局 | `start_bit`、`bit_length`、明确的位编号约定、大小端、符号/数值类型、复用条件 |
| 语义 | 名称、物理定义、factor、offset、单位、枚举表、来源 |
| 范围与有效性 | 可表示范围、观测范围、验证范围、无效码、有效条件、依赖定义 |
| 证据 | 候选竞争关系、未决项、标定记录、独立验证记录、输入与算法版本 |
| 生命周期 | 状态、定义哈希、审核记录、发布日期、撤销信息 |

例：某合成字段人为规定 raw=5000、factor=0.01、offset=0，则 physical=50。这仅说明 `physical = raw * factor + offset`，不证明它是任意实车上的车速。本设计不附带冒充实车成果的示例 DBC。

### 12.2 导出过程与产物

1. 选择目标车辆/总线范围和通过门槛的定义修订，冻结快照，检查选择器等传递依赖。
2. 按逻辑总线生成独立 DBC；名称冲突给出可追溯映射。扩展帧 ID 的格式编码交给适配器处理，内部仍保存纯仲裁 ID。
3. 使用 cantools 的消息/信号模型和导出接口，再严格加载。相关接口见 [cantools 文档](https://cantools.readthedocs.io/en/latest/)。
4. 核对重载后的 ID、帧类型、长度、位布局、比例/偏移、符号、单位、枚举、复用与原始快照等价；执行固定向量和独立日志回归。
5. 对目标消费工具检查 FD 属性、扩展复用、命名、中文注释编码等兼容性；不支持的语义明确阻断或从该目标发布范围排除，不静默降级。
6. 生成清单和验证报告，包完整校验后一次性发布。发布失败不推进状态；历史版本不覆盖。

建议发布包：

```text
<release>/
  <bus-a>.dbc          该逻辑总线已通过发布门槛的信号
  <bus-b>.dbc          仅在实际存在第二条发布总线时生成
  manifest.json       车型/软件/总线映射、工具版本、定义和文件哈希、使用限制
  validation.json     逐信号证据、阈值、指标、覆盖范围、审核与依赖
  unknown_fields.json 未解决位段、候选解释及缺失证据；不参与正式解码
```

DBC 导出不能完整表达的验证范围、完整性要求和超时规则必须保留在配套元数据与运行时适配中。单独拿到 DBC 不等于拥有安全使用许可。候选保存在内部模型/研究报告；若未来需要候选 DBC，必须采用独立研究导出入口和醒目标识，禁止混入正式发布包。

相同总线同 ID 若有无法在目标格式/工具中明确区分的长度或帧类型定义，应拆分适用 profile 或阻断导出，不能靠重命名消息掩盖解码键冲突。非线性换算、ISO-TP 重组、认证与完整协议状态机同样不能假装由 DBC 独立解决。

## 13. 建议技术栈

首选方案是 Python/FastAPI 本机应用服务、Vue 可视化页面、C++ 被动采集与 SQLite，统一打包为 Windows/Linux 应用。详细取舍和兼容性证明见[部署与可视化设计](deployment-and-ui.md)。以下尚未安装或锁定依赖，发布基线须先通过两端打包验证。

| 模块 | 建议 | 采用边界 |
| --- | --- | --- |
| 采集 | C++17；SocketCAN、周立功 SDK、创芯科技 SDK | 后端按系统/设备组合选取；共用原始模型；逐型号确认监听与 FD；ARM64 需另验 |
| 应用服务 | Python、FastAPI、Uvicorn，单一受管入口 | 同源提供 API 与页面；计算任务在受管子进程运行，不阻塞页面 |
| 可视化 | Vue 3、TypeScript、Vite、Element Plus、ECharts | 静态资源随包，首版完成全流程，不依赖 CDN 或 Node.js 运行服务 |
| 采集排查 | can-utils 等现有工具 | 仅使用符合被动策略的功能，工具存在发送能力不代表授权启用 |
| 离线分析 | Python、NumPy；按实际需要引入 SciPy/表格处理工具 | 先实现可解释统计和拟合，性能实测后再迁移热点到 C++ |
| DBC | cantools 导入、导出与回归 | 保留内部证据模型；消费工具兼容性单独验证 |
| 存储 | 原始分块文件 + JSON 清单 + SQLite | 大规模派生数据再考虑 Parquet；无需首版分布式服务 |
| 人工复核 | 自带位图、曲线、标签与候选比较页面；外部工具可辅助交叉检查 | 核心操作不要求另装 SavvyCAN 或手写脚本 |
| 发布 | PyInstaller onedir + 预编译采集器 + 已构建页面 | 按系统/架构独立构建；一个启动入口，运行环境随包；驱动与系统依赖需明示 |
| 在线消费 | C/C++ 解码库，按需求适配 ROS/OBTS Pilot | 位提取一致性、超时、有效性和版本门槛必须保留 |
| 测试 | 合成向量、录制日志、vcan、独立物理参考与台架 | 软件测试和硬件/实车验证分别报告 |

算法研究和机器学习可以后续补充候选排序，但不能替代确定性位提取、证据追溯或发布门槛。第三方工具/协议的许可证、目标平台和实际兼容性在采用前核验。

## 14. 分阶段开发路线与验收

每阶段交付可复现闭环，按证据进入下一阶段；不以“全车破解率”替代目标信号与适用范围的验收。

| 阶段 | 实现范围 | 退出门槛 |
| --- | --- | --- |
| P0 部署与采集基础 | 先验证 Windows/Linux 无开发环境打包启动与离线页面；再确定适配器、Classic/FD 模型、监听、时间/质量记录与回放 | 两端同一页面完成内置样例冒烟测试；分别实机证明被动采集；打包或硬件兼容失败不得只测开发环境后放行 |

## 15. 安全、数据与可追溯原则

- 默认只读/listen-only，拒绝自动回退主动模式；原始采集、离线回放和未来主动诊断必须具有清晰边界。
- 只在授权车辆与网络上工作；动态实验采用合适台架或封闭测试条件，由具备条件的人员执行，不为辨识未知信号注入实车控制报文。
- 候选不等于已验证；任何名称、相关性分数、模板匹配或解析成功都不能跳过独立验证。
- 安全相关控制只能使用独立验证通过且满足运行条件的信号。完整性、时效或适用性未知时不得输出有效控制输入。
- 原始证据只读保留，清洗、拟合、人工修订与撤销都有版本和来源；哈希保证内容可核对，但不单独证明采集真实性。
- 日志可能包含车辆标识、位置和行为信息；按最小必要范围采集、访问和共享。原始实车日志、凭据和受限 DBC 不默认提交 Git，脱敏副本不能替换原始证据。
- 对外来 DBC、日志和模板做大小/结构检查，不执行附带代码。不得把协议文件误当成允许联网、发报或控制车辆的指令。
- 工具/软件检查、台架验证、独立实车验证与安全控制准入分别报告；当前文档交付不构成其中任何一项已通过的证明。
